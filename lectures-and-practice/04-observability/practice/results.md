# Практика 04. Observability

Дата: 7 октября 2026 г.

## Запуск и проверка

- Grafana запущена, дашборд импортирован с UID `food-observability`.
- Оба сервиса запущены; health checks вернули HTTP 204.
- При нагрузке около 90–95 запросов в секунду проверены режимы `slow`, `error`, `timeout` и `normal`.
- В Grafana просмотрены метрики и логи Loki, в Jaeger — трейсы.

## Метрики

Сохранённые графики показывают общее пятиминутное окно с несколькими режимами. По ним нельзя надёжно разделить показатели по режимам. За время наблюдения успешность менялась примерно от 32% до 100%, в конце была около 70%. p95 колебался примерно от 1,5 до 4,2 с, p99 доходил примерно до 4,8 с. Это приблизительные значения с графиков.

| Режим | Что видно в сохранённых материалах |
| --- | --- |
| `slow` | Режим включался. Отдельные код ответа, Trace ID и длительность спана не сохранены. |
| `error` | Режим включался. Отдельные Trace ID и запись об отказе курьерского сервиса не сохранены. |
| `timeout` | В Loki есть запись с `mode=timeout`, `outcome=error` и ошибкой `context canceled`. Переход по её Trace ID в Jaeger вернул 404. |
| `normal` | После переключения графики вернулись к успешным ответам, но отдельный ответ после переключения не сохранён. |

## Трейс с HTTP 503

На снимке Jaeger [trace-503.png](./screenshots/trace-503.png) виден запрос:

- Trace ID: `bb5021ad7f172462344131fe2b1eaf0d`
- Время начала: `2026-10-07 12:53:28.606` по интерфейсу Grafana
- Запрос: `POST /orders`, ответ HTTP 503
- Длительность: 2 с
- В трейсе два сервиса и четыре спана: `order-service POST /orders` → `orders.create` → `HTTP POST` → `courier-service POST /reserve`

Длительность похожа на тайм-аут, но снимок не показывает атрибут `mode`. Связанные логи обоих сервисов с этим Trace ID также не сохранены, поэтому точную причину по этому трейсу установить нельзя.

## Запись timeout в Loki

- Trace ID: `33fbe51c1322b2d7fe18c9d66dfdd873`
- Сервис: `courier-service`
- Сообщение: `reservation failed`
- Время: `2026-10-07 12:43:48.739` по интерфейсу Grafana
- Ошибка: `context canceled`
- Поля: `mode=timeout`, `outcome=error`
- Span ID записи об ошибке: `03c789f7a6b674d6`

Для этого Trace ID Jaeger вернул 404. В Loki также есть отдельная запись `order completed` со Span ID `72242cd0b59bd2f9`; это не спан ошибки.

Отмена контекста согласуется с тайм-аутом исходящего запроса сервиса заказов: сервис перестал ждать, пока курьер завершит задержанную операцию. Поля Loki подтверждают отмену в режиме timeout, но для проверки всей цепочки нужен доступный трейс с тем же Trace ID и логи обоих сервисов.

## Ответы на вопросы

1. Counter накапливает число событий. Для частоты событий используют `rate(counter[5m])` — скорость прироста счётчика за последние пять минут.
2. Успешность считают среди завершённых попыток создания заказа: успешных плюс завершившихся ошибкой. Запросы без результата в знаменатель не входят.
3. p95 и p99 — оценки 95-го и 99-го перцентилей длительности за выбранное окно, рассчитанные по гистограмме. Это не длительности конкретных запросов.
4. Быстрые ошибки могут уменьшить p95 общей длительности, если учитываются в той же гистограмме. Поэтому p95 нужно смотреть вместе с долей успешных и быстрых успешных запросов.

## Что ещё нужно записать

Чтобы сравнить режимы отдельно, нужны точные времена их переключения и отдельный характерный Trace ID для каждого. Для трейса `bb5021ad7f172462344131fe2b1eaf0d` также нужны связанные логи обоих сервисов с тем же Trace ID и соответствующими Span ID.
