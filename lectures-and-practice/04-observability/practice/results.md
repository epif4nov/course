# Результаты практики по observability

Дата: 7 октября 2026 г.

## Выполненные действия

- Grafana запущена; дашборд импортирован под UID `food-observability`.
- Оба сервиса запущены, health checks вернули HTTP 204.
- Создана нагрузка примерно 90–95 запросов в секунду.
- Последовательно включены режимы `slow`, `error`, `timeout`, затем `normal`.
- В Grafana просмотрены панели, логи Loki и трейсы Jaeger.

## Наблюдения по дашборду

Сохранённые графики охватывают смешанное пятиминутное окно с несколькими режимами, поэтому значения нельзя приписать отдельному режиму. В этом окне доля успешных заказов менялась примерно от 50–100% и позднее была около 70%; p95 менялся примерно от 1,5–2 с до 4 с, p99 приближался к 5 с. Это приблизительные значения общего прогона, а не отдельные серии.

| Режим | Ожидаемый результат | Наблюдение |
| --- | --- | --- |
| `slow` | Успешный `201`, резервирование около 1,2 с; хуже доля быстрых успехов | Режим включён; отдельные HTTP-код, Trace ID и длительность спана не записаны |
| `error` | Быстрый `503`; отказ курьерского сервиса | Режим включён; отдельный Trace ID и текст лога курьеров не записаны |
| `timeout` | `503` примерно через 2 с; исходящий запрос отменяется | В Loki найдено `outcome=error`, `mode=timeout`, `error=context canceled`; по Trace ID из этой записи Jaeger вернул 404 |
| `normal` | Успешные `201` и начало восстановления графиков | Режим включён последним; отдельные ответ и восстановление после переключения не записаны |

## Трейсы и проблемный запрос

В Jaeger найден отдельный неуспешный запрос длительностью около двух секунд с двумя сервисами: `order-service` и `courier-service`; в дереве видны входящий HTTP-вызов, `orders.create` и вызов резервирования курьера. Этот трейс показывает межсервисную цепочку, но сохранённое изображение не позволяет надёжно сопоставить его Trace ID с timeout-записью из Loki.

Для timeout-записи Loki:

- Trace ID: `33fbe51c1322b2d7fe18c9d66dfdd873`
- Сервис: `order-service`
- Ошибка: `context canceled`
- Режим и исход: `mode=timeout`, `outcome=error`
- Span ID записи об ошибке `reservation failed`: `03c789f7a6b674d6`

Для этого Trace ID переход из Loki в Jaeger вернул 404, поэтому соответствующие спаны двух сервисов пока не подтверждены. Отдельная запись `order completed` имела Span ID `72242cd0b59bd2f9`; это другая запись, её не следует считать спаном ошибки.

Отмена контекста согласуется с тайм-аутом исходящего HTTP-запроса у сервиса заказов: клиент прекращает ожидание раньше завершения заданной задержки курьеров. Это объяснение поддерживается полями ошибки, но для доказательства полной причинной цепочки нужен доступный Jaeger-трейс именно с указанным Trace ID и парные логи обоих сервисов.

## Ответы на вопросы

1. Counter хранит накопленное число событий с момента запуска. Для скорости завершения используют `rate(counter[5m])`, среднюю частоту прироста за окно.
2. Знаменатель успешности — все завершённые попытки создания заказа с результатом success или error; запросы без результата не являются завершёнными.
3. p95 и p99 — оценки квантилей распределения за окно, рассчитанные по гистограммным бакетам. Это не точные длительности конкретных запросов.
4. Быстрые ошибки завершаются быстро и могут снизить p95, если входят в гистограмму длительности всех завершённых попыток. Поэтому p95 не заменяет долю успеха и долю быстрых успешных запросов.

## Что осталось зафиксировать

Для полной сдачи нужны отдельные записи по каждому режиму: время, HTTP-код, изменение панелей, характерный Trace ID, проблемный спан и связанный лог. Также нужен скриншот дашборда и скриншот одного проблемного трейса, у которого совпадают Trace ID и логи обоих сервисов. В доступных сохранённых наблюдениях для timeout-записи Jaeger ответил 404, а отдельный двухсервисный трейс не удалось уверенно сопоставить с её Trace ID.
