Это приблизительные значения общего прогона, а не отдельные серии.

| Режим | Ожидаемый результат | Наблюдение |
| --- | --- | --- |
| `slow` | Успешный `201`, резервирование около 1,2 с; хуже доля быстрых успехов | Режим включён; отдельные HTTP-код, Trace ID и длительность спана не записаны |

## Трейсы и проблемный запрос

На предоставленном скриншоте Jaeger (`Изображение ChatGPT 7 окт. 2026 г., 12_55_57.png`) найден конкретный неуспешный запрос:

- Trace ID: `bb5021ad7f172462344131fe2b1eaf0d`
- Начало: `2026-10-07 12:53:28.606` (время интерфейса Grafana)
- HTTP: `POST /orders`, ответ `503`
- Длительность: `2 s`
- Два сервиса и четыре спана: `order-service POST /orders` → `orders.create` → `HTTP POST` → `courier-service POST /reserve`.

Это подтверждает межсервисный трейс проблемного запроса. Его двухсекундная длительность согласуется с тайм-аутом, но на скриншоте не раскрыты атрибут mode и полные связанные логи обоих сервисов. Поэтому режим и корреляцию логов для этого Trace ID отдельно не утверждаем.

Для timeout-записи Loki:

- Trace ID: `33fbe51c1322b2d7fe18c9d66dfdd873`
- Сервис записи `reservation failed`: `courier-service`
- Время записи: `2026-10-07 12:43:48.739` (время интерфейса Grafana)
- Ошибка: `context canceled`
- Режим и исход: `mode=timeout`, `outcome=error`
- Span ID записи об ошибке `reservation failed`: `03c789f7a6b674d6`

Для этого Trace ID переход из Loki в Jaeger вернул 404, поэтому соответствующие спаны двух сервисов пока не подтверждены. Отдельная запись `order completed` имела Span ID `72242cd0b59bd2f9`; это другая запись, её не следует считать спаном ошибки.

Отмена контекста согласуется с тайм-аутом исходящего HTTP-запроса у сервиса заказов: клиент прекращает ожидание раньше завершения заданной задержки курьеров. Это объяснение поддерживается полями ошибки, но для доказательства полной причинной цепочки нужен доступный Jaeger-трейс именно с указанным Trace ID и парные логи обоих сервисов.

## Ответы на вопросы

1. Counter хранит накопленное число событий с момента запуска. Для скорости завершения используют `rate(counter[5m])`, среднюю частоту прироста за окно.
2. Знаменатель успешности — все завершённые попытки создания заказа с результатом success или error; запросы без результата не являются завершёнными.
3. p95 и p99 — оценки квантилей распределения за окно, рассчитанные по гистограммным бакетам. Это не точные длительности конкретных запросов.
4. Быстрые ошибки завершаются быстро и могут снизить p95, если входят в гистограмму длительности всех завершённых попыток. Поэтому p95 не заменяет долю успеха и долю быстрых успешных запросов.
